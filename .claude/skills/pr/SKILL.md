# pr

## Overview

Доводит текущую ветку до Pull Request на GitHub: прогоняет проверки из корневого `CLAUDE.md`,
пушит ветку и вызывает `gh pr create` с заголовком и телом по конвенциям проекта (раздел
«Ветки»). PR открывается всегда из текущей ветки — head аргументом не передаётся.

## Аргументы

```
/pr <title> [base_branch]
```

- **`$0`** — заголовок PR, обязателен. Формат — Conventional Commits, как заголовок коммита:
  `<тип>(<область>): <что делает>`, императив, без точки в конце, ≤ 72 символов (см. скилл
  `commit` — типы и область там же).
- **`$1`** — целевая (базовая) ветка PR, необязателен, по умолчанию `main`.

Если `$0` отсутствует — не подставлять и не выдумывать: остановиться и спросить у пользователя.

## Алгоритм выполнения

1. Разобрать аргументы: `title=$0`, `base_branch=${1:-main}`.
2. **`git status`** — рабочее дерево должно быть чистым. Есть незакоммiченные изменения —
   остановиться и сообщить, не трогать их и не запускать `stash`/`checkout` без явной просьбы.
3. Определить текущую (head) ветку: `git branch --show-current`. Она не должна совпадать с
   `base_branch` — PR ветки в саму себя бессмыслен, в этом случае остановиться с ошибкой.
4. **Проверить, нет ли уже PR у этой ветки:** `gh pr view --json url,state,number` (без
   аргумента — берёт PR текущей ветки). Если команда вернула результат — вывести пользователю
   найденный URL и остановиться, новый PR не создавать. Ошибка команды (PR не найден) — это
   ожидаемый путь продолжения, а не сбой.
5. **Проверить отставание от `base_branch`:** `git log HEAD..<base_branch> --oneline`. Если
   там есть коммиты — не мёржить автоматически, а предупредить пользователя и спросить, нужен
   ли `git merge <base_branch>` перед PR (см. «Ветки» в корневом `CLAUDE.md`: конфликт
   разрешает тот, кто видит контекст обеих сторон).
6. **Прогнать проверки из корня**, в этом порядке: `npm run build`, `npm run lint`,
   `npm run typecheck`, `npm test -w @expense-tracker/api`. Любая красная — остановиться,
   показать вывод и не создавать PR. Ветка уходит в PR только зелёной.
7. **`git diff <base_branch>`** (весь дифф ветки, не последний коммит) — источник для тела PR:
   что реализовано и какие эндпоинты добавлены/изменены (метод, путь, коротко по каждому — для
   веток, трогающих `apps/api`).
8. **`git push -u origin HEAD`.**
9. **`gh pr create`** с явными `--base <base_branch>`, заголовком из `$0` и телом, собранным на
   шаге 7, через heredoc:

   ```bash
   gh pr create --base <base_branch> --title "<title>" --body "$(cat <<'EOF'
   ## Что сделано
   - ...

   ## Эндпоинты
   - `METHOD /api/...` — ...
   EOF
   )"
   ```

   Раздел «Эндпоинты» опускается, если ветка не меняет `apps/api`.
10. Вывести пользователю ссылку на созданный PR из ответа `gh pr create`.

## Заголовок PR

Та же дисциплина, что у заголовка коммита (скилл `commit`): `<тип>(<область>): <что делает>`,
императив со строчной буквы, без точки, ≤ 72 символов. Если `$0` это нарушает — не переписывать
его молча, а сообщить пользователю, чем именно он не соответствует конвенции, и предложить
исправленный вариант.

## Запрещено

- Не переключать ветки — PR всегда открывается из той, на которой сейчас находится пользователь.
- Не мёржить `base_branch` в текущую ветку без явного подтверждения пользователя.
- Не открывать PR при красных проверках (шаг 6) и не пропускать их флагами вроде `--no-verify`.
- Не форс-пушить (`git push --force`) — если push отклонён, остановиться и спросить.
- Не создавать второй PR для ветки, у которой уже есть открытый (шаг 4).
- Не придумывать содержание тела PR — только то, что видно в `git diff <base_branch>`.

## Быстрая справка

| Вопрос                    | Ответ                                                            |
| -------------------------- | ------------------------------------------------------------------ |
| Аргументы                 | `$0` — заголовок (обязателен), `$1` — база (по умолчанию `main`) |
| Head-ветка PR             | Всегда текущая ветка, аргументом не передаётся                   |
| PR уже существует         | Сообщить и вывести ссылку, новый не создавать (шаг 4)             |
| Проверки перед PR         | `build`, `lint`, `typecheck`, `test -w @expense-tracker/api`      |
| Источник описания PR      | `git diff <base_branch>`, не последний коммит                    |
| Формат заголовка          | `<тип>(<область>): <что делает>`, императив, ≤ 72 символов        |
| Push                      | `git push -u origin HEAD`, без `--force`                          |
| Слияние базовой ветки     | Только по подтверждению пользователя                              |

## Частые ошибки

- Не проверить `gh pr view` перед созданием — тогда для одной ветки заводится второй PR-дубликат.
- Открыть PR по устаревшему дифу, когда `base_branch` ушёл вперёд, — сначала проверять
  отставание (шаг 5), иначе описание PR будет неполным.
- Пропустить проверки «раз и так всё работает» — красная ветка в PR превращает ревью в разбор
  поломок, а не фичи.
- Забыть `-u` при первом push ветки — тогда `gh pr create` не найдёт upstream и придётся
  повторять push вручную.
